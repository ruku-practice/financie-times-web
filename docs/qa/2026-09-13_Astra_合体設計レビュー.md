**合体の方向と決裁6項目は、このままでよいです。ただし、状態の所有者・共通データの定義・メンバー補正・夜間更新の接続は、着手前に具体化すべきです。** 手順1・2は現状のままでは独立していません。

**1. 構成：方針はよい／「出し先を渡すだけ」は変えるべき**

- `analysis.js` は `anState`・`anData`・`anCharts`・`dom` がIIFE内で各1個です。IDの接頭辞だけ変えても、2画面の状態とChartが混ざります。特に [`syncUrl()`](/Users/kkr/ruku_data/00_products/apps/FiNANCiE-times-web/.claude/worktrees/analysis-tab/js/analysis.js:899) は再描画のたびに `tab=analysis` を設定します。
- **小さく安全な案は、集計と箱単位の描画を分離し、旧分析タブはそれらを呼ぶ薄いラッパーとして残すこと。** 合体側では両ファイルの `init()`・`recomputeAll()` を呼ばず、必要な描画だけ呼びます。`overview.js` 側にもこの改修が必要です。
- 2か所で動かすなら、Chart・DOM・描画状態をインスタンスごとに分離し、`render(view, state, data)` と `dispose()` を定義。URL更新と共通操作のイベント登録は、ルーター／`merged.js`だけに限定します。
- `FtData.load()` は**通信中のPromiseも共有**してください。現在のoverviewは完了後の値しかキャッシュせず、同時呼び出しで重複取得します。遅延取得中に期間・見せ方が変わった場合は、古い描画結果を捨てる世代番号も必要です。
- IntersectionObserverは現状「一度見えたら監視解除」です。「現在見えている箱だけ更新」に変えるなら、可視状態と更新待ち状態を別に持ち、再表示時に最新状態で描きます。

**2. データ1系統化：よい／互換性と生成契約を追記すべき**

- **生のv24＋gapは適切**です。ただしgap判定は現行どおり「正の値かつ24H＝30日」。0＝0は欠測にしません。丸める前に判定し、元から取得不能のnullとも区別します。
- `market.v24_total` と `series.v24_total` を別々の定義で残すと、KPIと内訳が食い違います。**同じ行列・同じモードから合計、PJ数、順位、シェア、機運①〜③を算出する契約**が必要です。`days`・PJ順・精度・生成世代も全ファイルで揃えます。分析側の整数丸め／価格2桁をそのまま移植せず、overviewの精度を維持する案が安全です。
- **名寄せはv3.1の数字を変えます。** 実データではRED前身と後継に89日の重複があり、後継優先で除かれる前身の生出来高は159,712円です。「409→406だけの変更」ではありません。旧値との比較では、名寄せによる差と欠測による差を分けて検算します。
- 後継の表示名・slugを明示的に採用してください。現 `build_analysis.py` の「summaryで先に現れた行を採用」は、前身のメタデータが残る余地があります。
- `data/projects/`・`data/daily/`・`data/monthly/`を変更しなければ既存URLは維持できます。ただし、**合体画面は前身込み、リンク先の個別ページは後継だけ**になります。今回はその境界を注記し、旧folder URLも維持するのが小さい案です。
- **夜間接続は必須の追記です。** 調べたdaily／metadataワークフローと`update_daily.py`の生成経路には、両集計スクリプトの呼び出しがありません。履歴・summary確定後、`git add data/`前に統合集計と検証を入れ、失敗時は公開を止めます。metadata経由の再生成も対象です。
- 現overviewは合計約13.05MiB。追加するseries・monthly・bundlesは現形式で約0.16MiBなので、追加量自体は小さめです。ただし上部の機運④⑤にはメンバーと価格が必要で、**グラフを遅延描画しても、そのデータ取得は遅延できません**。初回通信量と展開後メモリを測定してください。

**3. 欠測の統一：決定はよい／水準・純増・レポート互換を分けて定義すべき**

- 現v3.1の①は「直前100人以上」「連続する0」「後に正値へ復帰」が条件です。設計文から100人条件が落ちています。nullを挟む区間、停止後の据え置き、新規PJの初回人数も明記してください。
- ②は「100人以上動くPJが20件」で日を検出し、**その日の同方向の変化は100人未満も除去、逆方向は残す**処理です。全PJの日次合計を一律0にする処理ではありません。6/24は実データでは補正後0でしたが、一般条件として固定しないでください。
- [`membersGapInfo()`](/Users/kkr/ruku_data/00_products/apps/FiNANCiE-times-web/.claude/worktrees/analysis-tab/js/overview.js:944) は水準を一斉変動分だけ補正していません。純増の描画時だけ差分を0にします。したがって、**生の水準の端点差から機運④を出すと、純増グラフと一致しません。**
- 具体案は、共通の補正済み日次差分から期間KPIと④を集計し、水準も揃えるなら、固定した起点からその差分を累積して「補正後水準」と表示すること。表示期間の先頭で補正をやり直してはいけません。
- **rawでもレポートのメンバー値とは一致しません。** レポートは0落ちを前値補完済みで、一斉再集計は水準に残す定義です。「記録どおり＝レポートと同じ」は出来高に限定してください。既存レポートの期待値は保存し、新モードの期待値を別に追加します。
- KPIのメンバー純増は現コードでは「選択期間」ではなく「機運の窓W」です。合体案どおり期間KPIにするなら、④用のW日純増と計算を分離します。

**4. テーマ：よい／対象と再描画経路を広げるべき**

- 属性なしをライトに変えるなら、両描画部品とadvancedの「`light`以外はdark」という判定も同時に変更します。CSSだけ反転すると初期表示で食い違います。
- `advanced.js`の個別・比較グラフにもテーマ更新を通知する必要があります。現在のテーマ切替はoverviewの再描画が中心です。非表示中のグラフは更新待ちにし、再表示で色を更新します。
- 追加対象は、ツールチップの背景・文字・枠、ドーナツの隙間、左右軸の色、グラデーション、上限▲。設計の変数一覧だけでは足りません。
- **`css/analysis.css`も対象に追加**してください。`#analysis-view`限定の高さ・リンク色・スマホ表の規則は、合体側へ移すと効かなくなります。
- 上位20・30があるので「10色統一」だけでは不足です。11系列目以降の色／線種と、folder単位の色・凡例IDを固定してください。`FtLegend`の現在の見本表示にも破線対応の追加が必要です。

**5. 検査：M1〜M10はよい／次の確認を足すべき**

- **通信・描画競合**：低速通信中の期間連打、タブ往復、同時取得、失敗→再試行、非表示中のテーマ変更。重複イベント・Chart残存・古い結果の上書きを確認。
- **URL互換**：旧`ov_*`、`an_*`、`?project=旧folder`、戻る／進む、分析から全体市況へ戻った後の再読み込み。`gap`省略と保存済みrawが衝突するため、共有URLを再現可能にする優先順位も決める。
- **数値の横断一致**：KPI＝日次合計＝ランキング全件合計＝円の全切片。週の端数除外・月次の別定義は、差が出る理由まで検査。
- **境界データ**：全0・全null・前期間不足・記録日欠落・初回人数・停止・復帰・名寄せ重複。現overviewは記録行数、analysisは暦日で期間を計算するため、共通期間処理は暦日に統一。
- **月次の先読み防止**：現[`monthly.json`生成](/Users/kkr/ruku_data/00_products/apps/FiNANCiE-times-web/.claude/worktrees/analysis-tab/scripts/build_analysis.py:285)はPJごとに1〜5日の値を採用する一方、`picked_days`は月共通の最初の候補日です。期末が翌月2日でも5日の値が混ざり得ます。PJ別採用日を保持して期末で制限するか、5日まで確定待ちにします。
- **実画面の検査**：分析テストの撮影補助はoverflowを強制変更します。合体のスクロール検査では変更せず、390／768／1280、縦横、全見せ方、44px操作領域を確認。
- 既存検査は定義変更だけでは足りません。分析データの待機URL、取得本数、固定色、DOM、保存キーも変更対象です。Playwrightの一時ディレクトリへの絶対参照も再現可能な依存指定へ直します。

**6. 実装順・並行化：変えるべき**

**手順0として、データ形式・補正式・期間境界・描画API・URLの所有者を先に確定**してください。これがないと手順1がJSONを決め、手順2が別の形を期待します。

その後なら、次の分担は独立させられます。

- **手順1**：生成器・ワークフロー・固定入力による数値検算。契約済みJSONを出力。

- **統合担当**：`FtData`・共通状態・overviewの描画分離・テーマ通知・画面配置・タブ経路を接続。

参照計算まで生成器と同時に同じ実装へ寄せると、同じ誤りで両方通ります。**旧期待値を保存し、独立計算と差分理由をレビューする工程**を残してください。
